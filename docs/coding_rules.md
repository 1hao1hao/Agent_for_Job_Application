# Coding Rules

## 基本原则

- 使用 Python 3.10+。
- 每次只实现一个模块，避免一次性铺开太多文件。
- 先实现最小可运行版本，再根据测试和失败样例优化。
- 优先使用标准库，只有当收益明确时才引入第三方依赖。
- 不做过度封装，不为未来假设提前设计复杂框架。
- 业务代码、测试、文档需要一起演进。

## 代码风格

- 核心函数必须有 type hints。
- 核心函数必须有 docstring，说明输入、输出和关键行为。
- 函数尽量短小，默认不超过一个清晰职责。
- 变量名表达业务含义，避免 `data`、`result`、`tmp` 这类含糊名称滥用。
- 复杂逻辑前可以写简短注释，但不要写重复代码含义的注释。
- 优先显式错误处理，不吞异常。

## 语言与注释规范

- 变量名、函数名、类名使用英文。
- docstring 和关键注释使用中文。
- 示例数据、测试数据、README、开发文档优先使用中文。
- 技术术语首次出现时给出中文解释，例如 RAG（检索增强生成）、BM25（经典关键词检索算法）、rerank（重排序）。
- 除非任务明确要求，不要生成英文 raw data。

## 模块边界

- `ingestion`: 只负责读取、清洗、切分和保存 chunk。
- `retrieval`: 只负责召回、打分、排序和引用候选。
- `routing`: 只负责 intent 和 source 选择。
- `agent`: 只负责流程编排和回答组织。
- `tracing`: 只负责 trace schema、记录和读取。
- `evaluation`: 只负责指标计算和评测报告。
- `utils`: 只能放真正通用的小工具，不能变成杂物间。

## 测试规则

- 每个新增模块必须有最小单元测试。
- 每个 bug fix 或失败样例都应尽量沉淀到 regression test。
- 测试样本要小，能快速运行。
- 测试优先覆盖行为，不依赖具体实现细节。
- 对 RAG 结果测试时，优先断言结构、rank、citation、指标，而不是完整自然语言答案。

## 文档规则

每次改动后必须总结：

- 改了哪些文件。
- 如何运行。
- 如何测试。
- 当前限制。
- 下一步建议。

重要设计选择记录到 `docs/decision_log.md`。

每次新增或重构模块时，必须能在任务总结或相关文档中说明：

- 新增或修改了哪个模块。
- 模块输入是什么。
- 模块输出是什么。
- 核心函数有哪些。
- 失败时怎么排查。
- 面试官如果问这个模块，应该怎么讲。

## 数据规则

- 原始数据放在 `data/raw/` 下，按 source type 分类。
- 处理后的 chunk 放在 `data/processed/chunks/`。
- 索引文件放在 `data/indexes/`。
- trace 输出放在 `traces/`。
- 不把真实隐私信息、账号、token、完整联系方式提交到样本数据中。

## 依赖规则

第一版默认不引入重型框架。

允许较早考虑的依赖：

- `pytest`: 测试。
- `pydantic`: 仅当 dataclass 不够表达 schema 时考虑。
- `numpy` 或 `scikit-learn`: 仅当实现 TF-IDF 或向量计算确有需要时考虑。

暂缓引入：

- LangGraph。
- LlamaIndex。
- LangChain。
- Vector database。
- Web framework。

## 输出规则

Agent 回答应尽量包含：

- 直接回答。
- 依据或引用。
- 不确定性说明。
- 可执行建议。

当没有足够证据时，系统应该明确说不知道或需要补充资料，不能编造。
